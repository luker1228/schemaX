<StepCard num="CM-02" label="命令契约">
  <SectionHead line1="pnpm 脚本" line2="名字固定，构建顺序承重" />
  <Note tag="pnpm">
    命令契约写死两件事：①<strong>脚本名固定</strong>——<code>pnpm dev</code>、<code>build</code>、<code>gen:component</code>，AI 要跑命令就用这些名字，不自创；②<strong>构建顺序是承重的</strong>——令牌 → 内容校验 → <code>astro build</code> → Pagefind 索引，前一步失败后面就不能跑。
  </Note>
  <Preview label="package.json" lang="json" code={`"scripts": {
  "dev": "astro dev",
  "tokens:build": "style-dictionary build",
  "content:check": "tsx scripts/validate-content.ts",
  "build": "tokens:build && content:check && astro check && astro build && search:build",
  "gen:component": "tsx scripts/gen-component.ts"
}`} />
  <Note tag="承重">
    顺序为什么不能乱：Pagefind 只对<strong>已构建的</strong> <code>dist/</code> 建索引，所以 <code>search:build</code> 必须排在 <code>astro build</code> 之后；令牌 CSS 必须在 <code>astro build</code> <strong>之前</strong>生成，否则组件拿不到颜色。这条链路写在 <code>build</code> 一行里，AI 改构建时不敢拆。
  </Note>
</StepCard>

<StepCard num="CM-03" label="lint 三层">
  <SectionHead line1="eslint + stylelint + prettier" line2="把规矩写成机器能查的规则" />
  <Note tag="eslint">
    三层各管一摊，由 <code>eslint-config-prettier</code> 解耦：Prettier 管格式、ESLint 管代码质量、Stylelint 管 CSS + token 约束。关键是——<strong>你把「不许硬编码颜色」写成 Stylelint 规则，AI 写错立刻被拦</strong>。规矩从「口头叮嘱」变成「机器强制的闸门」。
  </Note>

<StepCard num="CM-04" label="设计系统">
  <SectionHead line1="新增组件走一条命令" line2="数据驱动，不要手写" />
  <Note tag="工作流">
    设计系统页是<strong>数据驱动</strong>的：展示页用 <code>import.meta.glob</code> 自动捕获所有 demo 文件。所以新增组件走 <code>pnpm gen:component &lt;Name&gt;</code> 一条命令，它会同时生成组件本体、demo、并把 registry 标记为 <code>live</code>——刷新即生效。承重约定：<strong>不要手写组件文件、不要手改展示页</strong>。
  </Note>
  <Preview label="终端" lang="sh" code={`$ pnpm gen:component Button 主要、次要、幽灵变体

✔ 生成 src/components/design-system/Button.astro          （组件本体）
✔ 生成 src/components/design-system/demos/ButtonDemo.astro （演示）
✔ 更新 src/data/components-registry.ts                    （标记 live）`} />
  <Note tag="为什么承重">
    手写绕过脚手架，registry 和文件就会脱节——展示页要么漏组件、要么 demo 找不到报错。一条命令保证<strong>三处永远同步</strong>，AI 不必去理解三者的关联，照着规矩跑命令就行。
  </Note>
</StepCard>

<StepCard num="CM-05" label="schema 驱动">
  <SectionHead line1="schema 在边界，不在业务代码" line2="令牌是视觉真相的唯一来源" />
  <Note tag="schema 优先">
    「Schema 优先」不是「到处加 schema」。schema 只加在<strong>系统边界</strong>：构建期内容用 Zod / Content Collection、外部 API（GitHub）做运行时校验、跨窗口通信（Playground <code>postMessage</code>）用消息 schema、设计令牌用 DTCG JSON。普通业务逻辑只用 TS 类型——<strong>为了品牌理由在业务代码里到处加运行时 schema 是反模式</strong>。
  </Note>
  <Preview label="src/content.config.ts" lang="ts" code={`// 构建期内容边界 —— 这里该加 schema
const lessonSchema = commonFields.extend({
  slug: z.string(),
  course: z.string(),
  order: z.number(),
  presentation: z.enum(['scroll', 'board', 'stepper']),
});`} />
  <Note tag="令牌">
    设计令牌是<strong>视觉真相的唯一来源</strong>：以 DTCG JSON 在 <code>tokens/src/</code> 写，Style Dictionary 构建，全局只导入一次。业务代码禁用 <code>--sx-ref-*</code> 原语，只用 <code>--sx-sys-*</code> / <code>--sx-comp-*</code>，一个组件只能覆盖自己的 <code>--sx-comp-*</code>。结果：改一个色 = 改一处 token = 全站联动。
  </Note>
</StepCard>

<StepCard num="CM-06" label="怎么用" variant="reference">
  <SectionHead line1="改提示词，就是改 AI 的行为" line2="发现反复出错，就写进 CLAUDE.md" />
  <Note tag="杠杆">
    项目提示词是<strong>最高杠杆的文件</strong>：AI 每次进项目都读它，所以你改一行 <code>CLAUDE.md</code>，等于改了 AI 在<strong>所有任务</strong>里的默认行为。发现 AI 反复犯同一个错？别在对话里一次次纠正——把那条规矩写进 <code>CLAUDE.md</code>，一劳永逸。
  </Note>
